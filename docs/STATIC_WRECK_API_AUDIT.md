# Single static wreck-site API audit

Date: 2026-10-17. Target: Build 42.21, Steam client build 25485521. Documentation checkpoint at 0.1.0-dev.5; no runtime/API/configuration/save change or version bump. Inputs: the two [optimized local sites](STATIC_CRASH_MODEL_OPTIMIZATION.md), 24,969 and 24,986 triangles. One mesh/material includes each site's ground and debris. This audit implements nothing and does not authorize a probe, launch, installation change, deployment or publication.

**Verdict: CONDITIONAL for a later, separately reviewed decorative-object diagnostic. NO-GO for production crash placement with the original off-screen, collision, protected-identity or recovery guarantees.** A native GLB/static-IsoObject route exists. Loading these particular files successfully, their game appearance and dedicated synchronization are NOT TESTED. One mesh reduces the operation count; it does not establish an observer fence or a transaction.

## One anchor, rendering and collision

[VERIFIED] W03 `render(...)` first tries the model at `(x+0.5,y+0.5,z)`. Its `renderModel(...)` returns false when `PerformanceSettings.fboRenderChunk` is false, or no SpriteModel exists. It still accesses `this.sprite.getProperties()` after resolving a model: a model name does not make a null-sprite anchor safe. W17 returns NoModel, Loading, Failed or Ready as asset state changes. W03 can arrange delayed FBO rendering while loading. A separately specified fallback sprite is necessary for missing/unsupported rendering; an ordinary fallback image is not equivalent to a working 3D wreck.

[UNKNOWN] A helicopter-sized model may extend many tiles beyond the anchor. One object's render, lighting, occlusion and subscription ownership still begins at its square/chunk. This audit proves neither that the whole mesh stays rendered when only its distant tip is in view nor that a client can receive it when its anchor chunk is outside the client's retained set. FBO boundaries, chunk boundaries, camera pan/zoom, all local player viewports, cutaways, floors above, fog and occluding buildings require tests. Do not replicate one identical object into adjacent squares to repair culling; that creates duplicate world records and breaks the single-object contract.

[VERIFIED] W04 `AddTileObject(IsoObject,int)` snapshots IsoRegions flags at 5-6; performs native wall/door placement checks at 9-15; adds object membership at 16-56; calls addToWorld at 62-65 and RecalcAllWithNeighbours at 66-70; fixes placed offsets and invalidates LOS/light state at 78-139; notifies MapCollisionData, PolygonalMap2 and IsoRegions at 142-159; invalidates rendering at 160-166. Those notifications update the supplied square's engine state, not an inferred mesh-wide footprint. Do not append directly to `getObjects()` or call addToWorld a second time.

[VERIFIED] Character/grid collision in W04 `CalculateCollide(...)` reads square/property flags such as solid and solidtrans, independently of rendered triangles. W20 `calcPhysics(int,int,int,int[])` also reads `PhysicsShape` and `PhysicsMesh`; the latter resolves Bullet.physicsShapeNameToIndex at 1165-1247. WT05/W28/W29 identify a separate native physicsShape script/asset system. **Therefore custom native physics meshes exist; declaring collision impossible would be inaccurate.** This audit has not established a Lua-only, one-anchor, many-tile shape with matching player/zombie navigation, vehicle physics, LOS and cross-chunk updates. No collider is supplied by the optimized render GLB, nor does selecting it automatically select a PhysicsMesh.

Use no blocking or traversable-floor promise for an initial decorative diagnostic. A future solid wreck must independently verify collision/AI footprint ownership and removal. Extra invisible collision objects would change the user's literal single-object placement requirement and restore multiple-record recovery concerns; they are an alternative for review, not an approved fallback. A vehicle-backed wreck introduces another lifecycle and is not a verified substitute. Destruction, structural penetration, loot, salvage, fire and zombie attraction remain excluded.

SpriteModel records are shared. `getRotate()`, `getTranslate()` or setScale on a resolved shared record is not evidence of a durable per-object transform. Prefer a finite set of immutable named heading/scale variants, chosen by the server and serialized as the selected name. Arbitrary per-instance rotation/scale persistence and replication were not established. Do not mutate Base's global sprite/model state to rotate a single wreck.

## Publication, streaming and restart contract

[VERIFIED] W03 save writes non-null spriteModelName under nested flag 8192 at offsets 1222-1244; load reads it at 1462-1480. The saved value is the **SpriteModel definition name**, not the model asset path or all of its transforms. Definitions and asset bytes must remain present and compatible after restart/mod updates on every client. W04 square save/load traverse object records; W20 chunk serialization traverses squares. This supplies ordinary native persistence, not a durable commit acknowledgement to Lua.

[VERIFIED] Native complete publication W03 -> W19 -> W18 includes the regular object save record, then anchor coordinates, current list index and list-membership flags. W19 filters fully connected, currently relevant connections. W18 parses a native object, calls loadFromRemoteBuffer and then client processing adds it to the world and refreshes square/neighbor, roof, collision, pathfinding, light and render state. The packet's settings record reliability=3, ordering=1, handlingType=2 and LoginOnServer capability. This is native object transport; none of those fields is a cross-stream join/chunk or save-transaction fence.

Late joiners/out-of-range clients are not covered by that one broadcast. The native chunk path serializes/deserializes the same object records; W23 additionally has queued chunk transfer and disk SafeRead paths. [INFERRED] a normally saved anchor should therefore reconstruct the model selection on subsequent streaming/restart. [RUNTIME GATE] test creation overlapping an already prepared chunk download, unload/reload, reconnect and restart: prove one anchor/model, no stale sprite-only copy and no duplicate add. No new custom per-client spawn/replay protocol is justified by the source. Never call complete-object publication repeatedly as an unverified resync operation; W03 remote loading can add another object record and no stable-site deduplication was found in that path.

One object means no multi-component generation interval, but asynchronous asset loading can expose a fallback or delayed appearance, and a client with another chunk snapshot can have a different observation. Current relevance/distance checks, absence of a render callback and client visibility reports do not prove invisibility. [OFFSCREEN_SAFETY_DESIGN.md](OFFSCREEN_SAFETY_DESIGN.md) remains NO-GO for strict unseen materialization while clients connect, pan, teleport or stream. Setting fields before one insertion/publication improves consistency; it is not an observer-safe atomic commit.

All future placement coordinates, variant names, eligibility and outcome must be selected/validated on the server. Clients render native replicated objects, not authoritative local wrecks. No client may supply asset paths, trusted IDs, transforms, serialized objects or completion claims. Shared registry/cooldown/distribution settings, if later implemented, belong in authoritative sandbox options; protocol bounds and safe internal definitions are not balance settings. No settings added by this audit.

[NO-GO] Reliable automatic recovery after ambiguous save/removal is still unestablished. GlobalModData and chunk saves are independent; W22 captures a loaded chunk snapshot before its queued write. W24 mutates object metadata through native packets. An index, sprite name, coordinate, model name or client-editable siteId is not a protected identity, nor a tombstone that survives removal. Replaying a site after an absent object may restore a legitimately removed wreck, while trusting a registry-only completion may lose one. Do not auto-regenerate, issue loot or claim exactly-once placement. Retain/quarantine uncertain reservations and require reviewed manual disposition; full [persistence research](CRASH_PERSISTENCE_DESIGN.md) remains unresolved. A no-loot decorative diagnostic can test ordinary native save/reload without claiming cross-store recovery or production identity security.
