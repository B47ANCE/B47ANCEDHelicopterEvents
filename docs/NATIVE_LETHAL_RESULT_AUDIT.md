This supports a source-level serialized server-callback candidate. There is no yield, wait, custom acknowledgement or next-tick gap between kill and completion in the proposed boundary. It does not impose transport issue-time ordering across clients or prove every engine/native worker is globally serialized.

Ordinary player packet handlers remain untouched. L11 ZombieID.parse resolves the current server map at 12-29; its consistency requires a non-null zombie at 8-19. L12 PlayerHitZombiePacket.isConsistent composes that target check with normal player/weapon-hit checks. Thus a player hit parsed before terminal finalization runs through native combat; one parsed after removal fails target consistency. L08 then logs/synchronizes and returns before hit processing at 131-147. L12 logInconsistentPacket has a corpse-aware suppression branch at 31-93 when the wielder and shot ID match. No automatic ban is established by this ordinary missing-target branch; anti-cheat settings and client-side recoil/ammo/animation must still be tested.

For a prior ordinary lethal hit, a proposed support caller must skip an already dead/dying target and retain that native attribution/body. For a prior nonlethal hit, support can finish the remaining life through native terminal handling without setting an old positive health baseline. A player packet arriving after an already finalized death is governed by vanilla target rejection. These statements describe native processing order, not a guarantee that every client-observed swing wins a race or that latent hits are credited retrospectively. Positive-health/minimum-health correction, interception/recomputation of player damage, fabricated player attribution and resetting native guards remain excluded.

## Client completion, joins and known limits

L08 onClientPacket parses/checks consistency at 82-135, then postpones packets that request it at 150-160. L05 DeadCharacterPacket.isConsistent(IConnection):boolean requires a resolved live character; isPostponed():boolean returns true. L06 postpone():void registers the native pending corpse through its base at 0-3, then applies remaining current health as damage at 12-17. For a zombie, L17 NetworkCharacterAI.onDied():void processes that pending packet only when the server square corpse index is next (24-38); L18 PostponedPacket checks square/static-moving-object count at 0-37. L05 processClient(UdpConnection):void eventually calls dieNetwork with the native killer and completion listener at 493-514, whose callback sets the native corpse object ID, original online ID, reanimation and state lock. Client removal calls L32 GameClient.removeZombieFromCache(IsoZombie):void, which removes the online ID from IDToZombieMap at 0-20. This is an animation/order-aware native path, not immediate synchronous completion on all clients.

The following limits remain material:

- **Recent-death guard is bounded:** L10 NetworkZombieSimulator.parseZombie refuses to create a missing zombie if L03 IsoDeadBody.isDead(short) is true (54-87). That predicate checks registered corpses with matching character ID and age strictly below 0.1 world-age hours (42-65). It is not a permanent tombstone, a real-time delivery deadline or a Lua session/lease generation.
- **Unloaded/missing target:** the death packet cannot complete through L05's live-character path if that client cannot resolve the target. Its consistency branch returns before completion. L19 IsoGridSquare.save(ByteBuffer,ObjectOutputStream,boolean) serializes native corpses through staticMovingObjects at 421-549; load(ByteBuffer,int,boolean) restores them at 1015-1055. This is a native chunk-state recovery surface, not proof that an in-flight old chunk snapshot or join/teleport race includes the latest corpse. Late join/reconnect/streaming need dedicated evidence.
- **Short-ID reuse:** L20 IsoObjectID.allocateID():short increments/wraps the short counter and skips -1 at 0-34. No support incarnation marker accompanies native owner snapshots. Post-removal map-miss protection is bounded to that ID remaining unmapped; a later different target/current owner must not be conflated with the dead incarnation. No mod fix to native packet formats is proposed.
- **Failure/reentrancy:** native flags and cached body cover successful intact-instance execution. A thrown callback/native error, pool reuse, or clearing a guard is not covered by a durable receipt. Retain an in-flight exclusion for any future caller, freeze uncertain outcomes and inspect native evidence; do not retry or compensate by manufacturing a second death/body.
- **Persistence:** native corpse save capability does not atomically commit mission/ammo/item receipts, GlobalModData and chunk/player stores. No exactly-once across restart claim follows. MS03 and the existing persistence blockers remain separate.

The project-owned [offline branch model](../scripts/audit_lethal_interleavings.py) checks 17 named cases, including seven expected limitation counterexamples. It models successful serialized completion, player-first/support-first cases, post-removal snapshots/replay, setter-only failures, client guard expiry/body absence/missing target and ID reuse. It does not execute native calls, implement combat or reproduce an engine failure. Assumed native completion and later chunk contents are explicitly assumptions, not results proved by the model.

## Smallest reviewable next step and final verdict

**GO: native source audit completed.** The specific missing-entry/publication sub-blocker is narrowed by an identified vanilla Lua/native terminal path. **CONDITIONAL: design/review of a disposable, server-initiated, single-target lethal probe**, with one live eligible native zombie, server-side revalidation, two already loaded/fully connected relevant clients, no ID reuse, no third-party gameplay hooks and no custom health/result protocol. Known client/fixture readiness is a controlled test condition, not a production authority rule derived from client reports. The probe would observe native flags, corpse IDs/count, player-hit/loot attribution and receipts, never reset guards or reapply an uncertain result. Tests must then expand to latency/owner changes, missing targets, joins/restarts and patched/Linux compatibility; [L-R01-L-R10](SUPPORT_MP_TEST_PLAN.md) are all NOT TESTED.

**NO-GO: unrestricted production guarantee, nonlethal gunfire adapter or complete Military Air Support from this audit alone.** This is an unattributed terminal-death candidate, not a verified ranged Hit simulation, finite-ammunition mission, durable authorization loop or approved change to one-hit gameplay. Source finding review precedes a separate implementation request; engine launch requires separate authorization. No probe or gameplay was implemented.
